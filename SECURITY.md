# Security Policy

THE WORKSHOP handles member accounts, project files, private discussions, moderation data, and other community content. Security reports should be treated as private until they can be reviewed and corrected.

## Reporting a vulnerability

Do **not** open a public GitHub issue containing exploit details, credentials, private user information, or a proof of concept that could put a running community at risk.

Repository maintainers should configure GitHub **Private vulnerability reporting** (Security → Advisories) after the repository is created. Use that private channel when available.

If private vulnerability reporting has not yet been enabled, contact the repository owner through a private channel rather than publishing the report publicly.

Include:

- affected WORKSHOP version;
- affected route/feature;
- reproduction steps;
- realistic impact;
- suggested mitigation if known.

## Supported version

Until a formal long-term-support policy is established, only the latest tagged release should be considered supported.
